# Установка моста

Документ для человека и для агента. Агент читает `AGENTS.md`, человек — этот файл. Источник правды один, дублей нет.

## Что ставим

Мост между сайтом и расчётным ядром партнёрской программы. Стоит на сервере владельца, прячет ключ, держит привязку в cookie и принимает вебхуки.

Что нужно заранее:

- сервер с Docker и Docker Compose v2;
- домен или поддомен, который указывает на этот сервер (для HTTPS и cookie);
- ключ тенанта от сервиса расчётов;
- данные сайта: адрес, куда возвращать человека после перехода по ссылке.

## Что спросить у владельца

1. Ключ тенанта — строка вида `pn_...`. Если его нет, программа ещё не заведена: сначала тенант.
2. Адрес сайта, куда возвращать посетителя (`BRIDGE_DESTINATION_URL`).
3. Публичный адрес моста (`BRIDGE_PUBLIC_URL`) — обычно `https://partna.<домен>`.
4. Название программы для формы (`BRIDGE_BRAND`).

Остальные секреты скрипт выпускает сам.

## Шаги

```bash
git clone https://github.com/partna-dev/partna-bridge.git
cd partna-bridge
./scripts/install.sh
```

Скрипт идемпотентен: создаёт `.env` из шаблона, выпускает `BRIDGE_BRIDGE_TOKEN` и `BRIDGE_WEBHOOK_SECRET`, проверяет обязательные переменные, собирает контейнер, ждёт `/health` и печатает, что осталось.

Если скрипт остановился на «не заполнено», впишите значения в `.env` и запустите снова. Он не поднимает контейнер, пока переменные пустые.

## Проверки после установки

Каждая проверка должна дать ожидаемый ответ, иначе дальше идти нельзя.

| Проверка | Команда | Ожидание |
|---|---|---|
| Мост жив | `curl -fsS http://127.0.0.1:8020/health` | `"status":"ok"`, `"key_configured":true` |
| Ссылка работает | `curl -si https://<адрес>/r/TEST1 \| head -20` | `302` на сайт с `?ref=TEST1`, в ответе `Set-Cookie: pn_ref=TEST1` |
| Cookie защищена | там же | `HttpOnly`, `Max-Age=2592000` |
| Заказ без токена | `curl -si -X POST https://<адрес>/v1/order -d '{}'` | `401` |
| Вебхук без подписи | `curl -si -X POST https://<адрес>/webhooks/engine -d '{}'` | `401` |

Полный прогон уровня одной командой: `./scripts/smoke.sh --level 1 --url https://<адрес>`. Для
уровней 2 и 3 добавьте `--token`, `--code` и `--user`: скрипт пишет реальные факты, поэтому только на
тестовом коде.

## Вебхук в ядре

Без этого шага события привязки не доходят: ядро помечает их `skipped`.

```bash
partner-network webhook-set --tenant <тенант> \
  --url https://<адрес>/webhooks/engine \
  --secret <BRIDGE_WEBHOOK_SECRET из .env>
```

Проверить: `partner-network webhook-show --tenant <тенант>`.

Секрет в команде — тот же, что в `.env`. Если они разойдутся, мост ответит `401`, и это правильное поведение.

## Подключение к вебхуку платёжки

Мост не интегрируется с платёжным провайдером. Владелец вызывает `/v1/order` из своего обработчика вебхука — там, где он уже знает, что оплата прошла. Это один запрос в существующем коде, а не новая интеграция.

Оплата:

```bash
curl -X POST https://<адрес>/v1/order \
  -H "Authorization: Bearer <BRIDGE_BRIDGE_TOKEN>" \
  -H "Content-Type: application/json" \
  -d '{
    "eventId": "pay_2f9c",
    "occurredAt": "2026-11-19T12:00:00Z",
    "orderId": "1001",
    "memberId": "client-42",
    "amount": 350000,
    "currency": "RUB",
    "personalVolume": 0
  }'
```

Возврат:

```bash
curl -X POST https://<адрес>/v1/refund \
  -H "Authorization: Bearer <BRIDGE_BRIDGE_TOKEN>" \
  -H "Content-Type: application/json" \
  -d '{
    "eventId": "refund_7b1e",
    "occurredAt": "2026-11-25T09:30:00Z",
    "refundId": "r-1",
    "orderId": "1001",
    "amount": 350000,
    "currency": "RUB"
  }'
```

| Поле | Что передавать |
|---|---|
| `eventId` | идентификатор события в вашей системе: id платежа, транзакции или возврата |
| `occurredAt` | когда это произошло, ISO 8601 с часовым поясом |
| `orderId` | номер заказа в вашей системе |
| `refundId` | номер возврата, только для `/v1/refund` |
| `memberId` | покупатель — тот же `externalAccountId`, что и в `claim` |
| `amount` | сумма в минорных единицах: 350000 при `RUB` — это 3 500 ₽ |
| `currency` | три заглавные буквы: `RUB`, `KZT` |
| `personalVolume` | объём для расчёта; если программа его не использует, `0` |
| `productId`, `retailAmount`, `certificateAmount` | необязательные: товар, розничная сумма, оплата сертификатом |

Что важно:

- **`eventId` должен быть устойчивым.** Провайдер повторяет вебхук, пока не получит `200`. Очередь моста отбрасывает повтор по `eventId`, ядро делает то же — но только если идентификатор тот же. Случайный UUID на каждый вызов превратит один платёж в два заказа.
- **Только по факту успеха.** При `pending`, `canceled` или ошибке оплаты заказа быть не должно.
- **`memberId` — покупатель, не партнёр.** Привязка к партнёру берётся из `claim`. Если покупатель не проходил по ссылке `/r/<код>`, заказ пройдёт, а комиссии не будет.
- **`refund` нужен, чтобы ядро откатило начисление.** Отправлять после того, как деньги реально вернулись клиенту.

Ответ в режиме `queue` — `202` и `{"queued": true, "eventId": "..."}`: факт лёг в очередь, обработчик может отвечать провайдеру `200` и не зависеть от доступности ядра. В режиме `inline` ответ `200` означает, что ядро приняло факт сразу, а ошибка ядра вернётся с её кодом.

## Очередь событий

По умолчанию `BRIDGE_OUTBOX_MODE=queue`: заказ и возврат пишутся в локальную очередь и отвечают `202`, воркер досылает их с повторами. Это защищает от потери факта, когда ядро недоступно.

- `GET /v1/outbox` — что в очереди и с какими ошибками;
- `POST /v1/outbox/{id}/retry` — повторить вручную;
- `GET /v1/inbox` — принятые вебхуки.

Оба требуют `Authorization: Bearer <BRIDGE_BRIDGE_TOKEN>`.

Если владельцу нужно мгновенное подтверждение начисления, поставьте `BRIDGE_OUTBOX_MODE=inline`: заказ уйдёт сразу, но при недоступности ядра вернётся ошибка, а факт придётся отправлять заново.

## Ошибки

**`key_configured: false`** — пустой `BRIDGE_ENGINE_API_KEY`. Заполнить и `docker compose up -d --force-recreate`.

**`503 bridge token is not configured`** — пустой `BRIDGE_BRIDGE_TOKEN`. Запустить `./scripts/install.sh` снова.

**`401 invalid api key` от ядра** — ключ не от этого тенанта или отозван. Выпустить новый на стороне сервиса расчётов.

**Cookie не появляется** — почти всегда `http` вместо `https` или другой домен. Cookie ставится на домен моста, поэтому мост должен жить на домене сайта или его поддомене.

**CORS в браузере** — в `BRIDGE_ALLOWED_ORIGINS` должен быть точный адрес фронтенда, без слэша на конце.

**Событий нет в `/v1/inbox`** — вебхук в ядре не настроен или секрет другой. Смотреть `webhook-show` и логи моста.

## Чего не делать

- Не вписывать ключ тенанта в код фронтенда и не отдавать его браузеру.
- Не открывать `/v1/order` и `/v1/refund` наружу без токена.
- Не коммитить `.env`.
- Не менять `BRIDGE_WEBHOOK_SECRET` без обновления секрета в ядре: события начнут отклоняться.

## Готово, если

- `/health` отвечает и ключ настроен;
- `/r/<код>` ставит cookie и возвращает на сайт с `?ref=`;
- заказ без токена получает `401`, с токеном — `202` (очередь) или `200` (inline);
- вебхук с валидной подписью отвечает `200`, повтор помечается `duplicate`;
- `webhook-show` показывает адрес моста.
