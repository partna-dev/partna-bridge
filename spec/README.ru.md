# Контракт фактов, версия 1

[English](README.md) · Русский

Пять операций, из которых состоит вся запись в партнёрскую программу. Всё
остальное — чтение (кабинет) и настройки (кабинет владельца), они в этот
контракт не входят.

- `POST /v1/claim` — привязать клиента к коду партнёра;
- `POST /v1/member` — участник программы и от кого он пришёл;
- `POST /v1/order` — клиент оплатил;
- `POST /v1/refund` — клиенту вернули деньги;
- `POST /v1/partner-link` — ссылка партнёра для его клиентов.

Схема: [`partna-facts.v1.json`](partna-facts.v1.json) — OpenAPI 3.1. Примеры
запросов: [`examples/`](examples).

## Авторизация

`POST /v1/claim` принимает код партнёра и доступен без токена: его вызывает
браузер при регистрации или бэкенд владельца. Остальные четыре операции требуют
заголовок:

```
Authorization: Bearer <BRIDGE_TOKEN>
```

Ключ тенанта (`X-API-Key`) в этот контракт не входит: он живёт в переменных
окружения моста и в браузер не попадает.

## Идемпотентность

У каждой записи есть `eventId` — его генерирует отправитель, а не мост. Правило
простое: один факт — один `eventId`, навсегда. Повторная отправка с тем же
`eventId` не должна приводить к повторному начислению.

- ядро отвечает `duplicate: true`, если событие уже принято;
- мост в режиме очереди кладёт событие в outbox и отвечает `202`;
- `eventId` короче 200 знаков, обычно это `order:<id>`, `refund:<id>`,
  `member:<id>`, `claim:<код>:<клиент>`.

## Ответы

| Операция | Ответ |
|---|---|
| `claim` | `{status, code?, sponsorId?, memberId?, claimedAt?, eventId?}` |
| `order`, `refund`, `member` | `{queued, eventId, engine?: {eventId, status, duplicate}}` |
| `partner-link` | `{code, url, expiresAt}` |

Поля, которых нет в примерах, сохраняются: контракт расширяемый, лишние поля от
ядра не выбрасываются. Клиент обязан игнорировать незнакомые поля.

## Ошибки

| Код | Когда | Тело |
|---|---|---|
| `400` | нет кода партнёра, кривое тело, плохой код ссылки | `{"detail": "..."}` |
| `401` | нет или неверный `Authorization` | `{"detail": "unauthorized"}` |
| `409` | перепривязка к другому партнёру, занятая ссылка | `{"detail": "..."}` |
| `422` | тело не проходит схему | `{"detail": [...]}` |
| `429` | больше 30 `claim` в минуту с адреса | `{"detail": "too many claims"}` |
| `503` | не задан токен или ключ тенанта | `{"detail": "..."}` |

## Что считается совместимым изменением

- добавление необязательных полей в ответы и новые операции;
- новые значения `status`;
- расширение допустимых значений, если клиент и так их пропускает.

Несовместимо: удаление и переименование полей, смена смысла сумм, перенос
маршрутов, изменение единиц. Суммы всегда в минорных единицах валюты
(`amount: 500000` — это 5 000,00 ₽).

## Как контракт держится в актуальном виде

Схема собирается из самих обработчиков (`src/partna_bridge/spec.py`), а не
пишется руками:

```bash
uv run python scripts/export_spec.py          # обновить снимок
uv run python scripts/export_spec.py --check  # проверить, что снимок свежий
```

Тесты `tests/test_contract.py` проверяют три вещи: снимок совпадает с
приложением, в контракте ровно пять операций, примеры проходят по схемам.
Расхождение валит пайплайн, а не всплывает у клиента.
