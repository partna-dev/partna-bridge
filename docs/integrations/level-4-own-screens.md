# Уровень 4 — свои экраны

Владелец показывает партнёру его баланс и выплаты внутри своего кабинета. Партнёр остаётся клиентом
владельца и не уходит на чужой домен.

Мост в этом уровне не участвует: чтение идёт напрямую из ядра по ключу тенанта, который и так живёт
на сервере владельца. Проксировать чтение через мост незачем — cookie и очередь нужны только для
записи фактов.

## Три способа, от простого к полному

### 1. Отдать готовый кабинет ссылкой

```bash
curl https://networks.partna.dev/v1/portal/partners/iron/access-link \
  -H "X-API-Key: $PARTNER_NETWORK_API_KEY"
```

Ответ: `{"url": "https://networks.partna.dev/p/<токен>", "expiresAt": "..."}`. Владелец кладёт
ссылку в своё письмо или в свой кабинет, партнёр открывает и видит баланс, приглашённых и выплаты.

Плюс: ноль работы. Минус: домен наш, а не владельца.

### 2. Кабинет на поддомене владельца

Тенанту задаётся домен, и кабинет открывается уже на нём:

```bash
partner-network domain-set --tenant aisunrise --domain partners.aisunrise.ru
```

Название, логотип, цвета и текст поддержки задаются в настройках тенанта. Тогда партнёр видит бренд
владельца, а не наш.

### 3. Свои экраны на своих данных

Ядро отдаёт готовые срезы, владельцу остаётся нарисовать таблицу.

```
GET /v1/portal/partners/{memberId}           сводка, приглашённые, выплаты
GET /v1/portal/partners/{memberId}/invited   только приглашённые
GET /v1/portal/partners/{memberId}/payouts   только выплаты
```

Авторизация: `X-API-Key: <ключ тенанта>`, серверный вызов. Ключ нельзя отдавать в браузер.

Что в сводке:

| Поле | Смысл |
|---|---|
| `netEarnedMinor` | начислено за всё время, минорные единицы |
| `paidMinor` | выплачено |
| `pendingPayoutMinor` | в партии, ожидает подтверждения |
| `availableMinor` | доступно к выплате |
| `heldMinor` | на удержании |
| `invitedCount`, `activeInvitedCount` | сколько приглашено и сколько активно |

Пример на бэкенде:

```ts
const response = await fetch(
  `${ENGINE_URL}/v1/portal/partners/${memberId}`,
  { headers: { "X-API-Key": process.env.PARTNER_NETWORK_API_KEY! } },
);
const dashboard = await response.json();
const available = dashboard.summary.availableMinor;
```

## Что владелец показывает в своём кабинете

Минимум, который закрывает вопросы партнёра: доступно к выплате, начислено за месяц, список
приглашённых с их начислениями, история выплат и ссылка для клиентов.

Ссылку для клиентов владелец уже получает на уровне 2 (`/v1/partner-link`) и хранит у себя.

## Про события в реальном времени

Если владельцу нужно узнавать о начислениях сразу, а не запросом, есть `GET /v1/inbox` на мосту:
там лежат принятые вебхуки ядра, дедуплицированные по `eventId`. Опрашивать раз в минуту дешевле,
чем строить отдельный канал.

Пересылки вебхуков с моста на адрес владельца пока нет: одно событие, один получатель. Если она
понадобится, это отдельная работа, а не настройка.

## Порядок внедрения

1. Уровень 2 или 3 — чтобы факты уже шли.
2. `access-link` или поддомен — чтобы партнёр видел цифры без работы владельца.
3. Свои экраны — когда появятся требования к вёрстке и своим данным.

## Чего не делать

- Не отдавать ключ тенанта в браузер: это тот же ключ, которым пишутся заказы.
- Не кешировать сводку дольше нескольких минут: после закрытия периода цифры меняются.
- Не показывать `pendingPayoutMinor` как «скоро на счёт»: деньги ещё в партии, статус может
  измениться.

## Доступ партнёра: ссылка или его аккаунт

Платформа по умолчанию не требует от партнёра регистрации. Владелец выдаёт ссылку
`/p/<токен>`: она живёт 30 дней, открывается повторно и продлевается при каждом заходе,
поэтому активный партнёр не упирается в срок, а неактивный отваливается сам. Для «открыть
сейчас» есть одноразовый вход на 15 минут.

Если владелец не хочет никаких ссылок, единственный честный путь — показывать кабинет
внутри своего продукта, то есть этот уровень. Партнёр входит своим обычным аккаунтом у
владельца, а бэкенд читает сводку и выплаты из ядра по ключу тенанта.

Мост в этом не участвует: он нужен для привязки и фактов, а чтение идёт напрямую из ядра.
Проксировать чтение через мост смысла нет — ключ и так на сервере владельца.
