# Уровень 3 — свой граф

Владелец сам ведёт структуру: у него есть коды, ссылки и CRM, где уже записано, кто кого пригласил.
Ядро в этом режиме только считает. Такое же поведение описано в документации ядра как режим
«хост владеет атрибуцией».

Мост нужен для двух вещей: спрятать ключ и не потерять факты, когда ядро недоступно.

## Кто источник истины

Владелец. Он присылает три вида фактов:

| Факт | Когда |
|---|---|
| `member` | у человека появился устойчивый идентификатор; у приглашённого — вместе с пригласившим |
| `order` | оплата подтверждена |
| `refund` | деньги вернулись клиенту |

`claim` на этом уровне не нужен: связь приходит в `member`, а не выводится из кода.

## Участник

```bash
curl -X POST https://partna.client.com/v1/member \
  -H "Authorization: Bearer $BRIDGE_BRIDGE_TOKEN" \
  -H "Content-Type: application/json" \
  -d '{
    "eventId": "member:user-42:iron",
    "occurredAt": "2026-11-19T12:00:00Z",
    "memberId": "user-42",
    "sponsorId": "iron",
    "placementId": "iron"
  }'
```

Поля:

| Поле | Обязательное | Что значит |
|---|---|---|
| `eventId` | да | детерминированный идентификатор: `member:<id>:<спонсор или root>` |
| `occurredAt` | да | когда это событие произошло у владельца |
| `memberId` | да | идентификатор человека в системе владельца |
| `sponsorId` | нет | кто пригласил; без него участник становится корнем |
| `placementId` | нет | куда поставить в дереве; для unilevel обычно равен `sponsorId`, для matrix задаёт место |
| `leg` | нет | `left` или `right` для бинарных структур |
| `status` | нет | `active` (по умолчанию) или `inactive` |

Статус `blocked` через этот вызов поставить нельзя: блокировку делает владелец в кабинете, это
управленческое решение, а не факт ingestion.

## Правила связывания

- **Поздняя привязка работает.** Пришли сначала заказы, потом участник — ядро держало их как
  `pending_member` и разрешит, когда участник появится. Порядок отправки можно не соблюдать.
- **Корень можно укоренить.** Участник, который был корнем без спонсора, приходит второй раз со
  спонсором — ядро переставит его.
- **Уже вложенного перепривязать нельзя.** Другой спонсор — `409`, и это защита, а не сбой.
- **Неизвестный спонсор** — `422`, факт не записан.
- **Заблокированный спонсор** — привязка отклоняется.

## Заказы и возвраты

Те же вызовы, что на уровнях 1 и 2:

```bash
POST /v1/order    # amount в минорных единицах, memberId = покупатель
POST /v1/refund   # чтобы ядро откатило начисление
```

`eventId` заказа стройте из идентификатора платежа: `order:<провайдер>:<id>`. Так повтор вебхука
провайдера не засчитается дважды.

## Очередь

Все три вызова по умолчанию работают в режиме `queue`: ответ `202`, факт лежит в SQLite, воркер
досылает с backoff. Если ядро вернёт `409` или `422`, запись останется в очереди с текстом ошибки —
разбирать нужно руками, потому что повтор не поможет.

```bash
GET  /v1/outbox          # что не ушло и почему
POST /v1/outbox/{id}/retry
```

## Проверка

```bash
./scripts/smoke.sh --level 3 \
  --url https://partna.client.com \
  --token "$BRIDGE_BRIDGE_TOKEN" \
  --user test-42
```

Скрипт создаст участника без спонсора. Если после него запустить с `--user test-43 --sponsor test-42`,
второй участник встанет под первого.

## Чего здесь нет

Владелец не видит начислений в своём интерфейсе — только в кабинете на нашем домене или через
чтение из ядра (уровень 4). Блокировка партнёра — тоже там.
