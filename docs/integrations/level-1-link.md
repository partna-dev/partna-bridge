# Уровень 1 — готовая ссылка

Самый простой уровень: владелец не пишет интеграцию, партнёр не регистрируется нигде, кроме сайта
владельца. Партнёр получает ссылку, клиенты приходят по ней, деньги считаются по заказам.

## Кто что делает

| Кто | Что |
|---|---|
| владелец | заводит партнёра в кабинете, отправляет ему ссылку |
| партнёр | размещает ссылку, приводит клиентов |
| клиент | регистрируется на сайте владельца как обычно |
| фронтенд владельца | один вызов `claim` в момент регистрации |
| бэкенд владельца | отправляет `order` и `refund` |

## Шаги

1. Мост установлен на домене владельца или его поддомене, например `partna.client.com`. Это условие
   для cookie: она ставится на домен моста.
2. В кабинете владельца `https://networks.partna.dev/cabinet` в разделе «Партнёры» нажать
   «Добавить партнёра», указать имя. Кабинет выдаст код и ссылку.
3. Ссылка партнёра выглядит так:

   ```
   https://partna.client.com/r/IRON
   ```

   Если владелец хочет короткий адрес на своём домене, это обычный редирект на ссылку моста.

## Что происходит при переходе

`GET /r/IRON` ставит cookie `pn_ref=IRON` (`HttpOnly`, `SameSite=Lax`, 30 дней) и возвращает `302` на
`BRIDGE_DESTINATION_URL` с добавленным `?ref=IRON`.

Cookie живёт на домене моста и отправляется только запросам к мосту. Это нормально: `claim` вызывается
на мосту, а не на сайте владельца.

## Что добавить на фронтенд

Один вызов в момент, когда у человека появился устойчивый идентификатор в системе владельца
(после регистрации или входа):

```ts
await fetch("https://partna.client.com/v1/claim", {
  method: "POST",
  credentials: "include",
  headers: { "Content-Type": "application/json" },
  body: JSON.stringify({ externalAccountId: user.id }),
});
```

`code` можно не передавать: мост возьмёт его из cookie. Если владелец хочет привязывать по параметру
из адреса, а не по cookie, — передать явно:

```ts
body: JSON.stringify({ code: new URLSearchParams(location.search).get("ref"), externalAccountId: user.id }),
```

Домен фронтенда должен быть в `BRIDGE_ALLOWED_ORIGINS`, иначе браузер заблокирует запрос.

## Что добавить на бэкенд

Заказ в момент подтверждённой оплаты:

```bash
curl -X POST https://partna.client.com/v1/order \
  -H "Authorization: Bearer $BRIDGE_BRIDGE_TOKEN" \
  -H "Content-Type: application/json" \
  -d '{
    "eventId": "pay_2f9c",
    "occurredAt": "2026-11-19T12:00:00Z",
    "orderId": "1001",
    "memberId": "user-42",
    "amount": 350000,
    "currency": "RUB",
    "personalVolume": 0
  }'
```

`memberId` — тот же идентификатор, что уходил в `claim`. `amount` — в минорных единицах.

Ответ `202` означает «факт в очереди», ошибку ядра владелец увидит в `/v1/outbox`.

## Проверка

```bash
./scripts/smoke.sh --level 1 --url https://partna.client.com
```

Ожидается: `/health` отвечает, `/r/TEST1` отдаёт `302` и ставит `pn_ref=TEST1`.

## Частые ошибки

- **Cookie не появляется** — мост открыт по `http`, а не `https`, либо ссылка ведёт на другой домен.
- **`claim` отвечает `400 partner code is missing`** — человек пришёл не по ссылке и cookie нет.
  Это нормальный случай: клиент без партнёра.
- **`claim` отвечает `429`** — сработал браузерный лимит (30 в минуту с адреса). Для серверных
  вызовов есть уровень 2.
- **Начислений нет, хотя заказы идут** — `memberId` в заказе не совпадает с `externalAccountId`
  в `claim`.

## Чего на этом уровне нет

Владелец не может показать партнёру баланс у себя: партнёр смотрит кабинет на нашем домене или
получает ссылку от владельца. Если это мешает — уровень 4.
